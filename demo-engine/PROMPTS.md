# 결정론 수박게임 시연 엔진 — STEP별 프롬프트

각 STEP의 회색 블록을 **통째로 복사해** AI 코딩 에이전트에 붙여넣습니다.
STEP 끝의 **게이트**는 사람이 직접 확인합니다. AI의 "검증 완료" 자평으로 대체하지 마세요 — 이 계열 프로젝트에서 그 자평이 반복해서 틀렸습니다.

---

## 전 STEP 공통 규칙 (프롬프트마다 다시 넣을 것)

```
[불변 규칙]
- 화면은 정수 프레임 f 하나만 받는 순수 함수다. window.__seekF(f) 를 호출하면 그 순간 그림이 나온다.
- 금지: requestAnimationFrame · Math.random() · Date.now() · CSS transition/@keyframes · filter:blur
- 물리는 렌더 안에서 돌리지 않는다. 오프라인에서 고정 dt·고정 시드로 한 번 굽고,
  렌더러는 프레임별 스냅샷을 조회만 한다.
- 화면에 뜨는 숫자·배지·팝업은 전부 "시뮬이 기록한 사건에서 파생"돼야 한다.
  손으로 적은 문자열·시간 스케줄로 띄우지 마라.
```

마지막 줄이 핵심입니다. 나머지는 결정론을 위한 배관이고, 저 줄은 **정직성**을 위한 것입니다.

## STEP 1 — 과일 형태 데이터 (SVG → 수학값)

> 이 저장소의 [`extra/fruit_vec.json`](../extra/fruit_vec.json)·[`extra/svg2fruit.py`](../extra/svg2fruit.py)·[`svg/`](../svg/)가 이 STEP의 산출물입니다. 그대로 가져다 쓰면 이 STEP은 건너뛰어도 됩니다(파일별 라이선스 = [`NOTICE.md`](../NOTICE.md) — 추출기·자작 SVG는 CC0, Noto Emoji 유래 8종은 Apache-2.0).

AI 코딩 에이전트는 그림을 그리지 못합니다. 캔버스에 과일을 "그려 달라"고 하면 색 있는 원이 나옵니다. 그래서 **형태는 SVG에서 가져오고, AI에게는 구조 변환만** 시킵니다.

````프롬프트
`svg2fruit.py`를 만들어라. 표준 라이브러리만 쓴다(의존성 0).

입력 = SVG 파일들. 출력 = `fruit_vec.json`.

- SVG path의 `d` 를 직접 파싱한다. M/m C/c S/s L/l H/h V/v Q/q T/t A/a Z/z 전 명령 지원.
  L·H·V·Z 는 큐빅으로 승격, Q·T 는 큐빅으로 변환, S·T 는 직전 제어점 반사, A(호)는 직선 근사 + 경고 출력.
- `circle`·`ellipse` 요소는 4호 큐빅 근사(제어점 계수 0.5523).
- `fill="url(#id)"`(그라디언트)는 첫 불투명 stop 색으로 근사한다.
- 정규화: viewBox 중심 → 원점, `R = max(vbW,vbH)/2` → 1. y-down 캔버스계 유지. 좌표는 소수 4자리 반올림.
- `path` 요소 하나 = 1레이어. 서브패스 그룹을 유지해 nonzero 구멍(씨앗·잎 틈)을 보존한다.
- 스키마: { 과일명: [ { fill, subs: [ [ [x0,y0,c1x,c1y,c2x,c2y,x1,y1], ... ] ] } ] }

검증:
  (a) 같은 입력으로 2회 실행 → JSON 바이트 동일
  (b) 과일별 레이어 수·큐빅 세그먼트 수를 표로 출력
  (c) 캔버스 Path2D로 재생해 원본과 대조할 수 있는 정적 HTML 뷰어를 함께 만들어라.
      회전각은 프레임의 순수 함수(a = f*0.03)로 두고 슬라이더로 앞뒤로 훑을 수 있게 한다.
````

**소스를 고를 때**

- 라이선스가 명시된 이모지 세트를 쓰세요(예: Noto Emoji = 이미지 리소스 Apache 2.0).
- **수박게임은 "잘리지 않은 통과일" 실루엣이 필요합니다.** 대부분의 이모지 수박은 슬라이스입니다. 없는 과일(통수박·감)은 직접 그려야 합니다 — 평면 색 몇 개면 충분합니다.
- 그라디언트 채움 과일은 대표 stop색 근사에서 **잎 색이 바디로 번집니다**. 그런 과일도 평면으로 다시 그리는 편이 빠릅니다.
- 티어 구분은 색이 아니라 **실루엣**으로 하세요. 실제 과일색을 쓰면 색이 겹치는 티어가 생기는데, 통과일 실루엣이 다르면 그래도 구분됩니다.

**게이트 1**: (a) 2회 실행 바이트 동일 · (b) 티어 수만큼 과일이 있고 레이어/세그먼트가 0이 아님 · (c) 뷰어에서 전 과일이 원본처럼 보임(육안).

## STEP 2 — 결정론 물리 베이크 코어

````프롬프트
`suika_bake.cjs`를 만들어라. planck.js(Box2D 포트) 강체 시뮬을 **고정 dt·고정 시드**로 굽고
프레임별 스냅샷을 JSON으로 직렬화하는 오프라인 스크립트다. 렌더링 코드는 들어가지 않는다.

[불변 규칙] (위 공통 블록 붙여넣기)

세계:
- 단위 = 미터, y-up. 중력 (0, -22)  ← 강한 중력 = 낙하감. 실제 g가 아니라 연출값이다.
- FPS 30, 프레임당 서브스텝 4, dt = 1/(30*4) 고정. 가변 dt 금지.
- 컨테이너: 내부 폭 7.2 · 높이 12.8 · 벽 두께 0.2. 바닥·좌우 벽은 정적 바디.
- 과일 물성: density 1.0 · friction 0.35 · **restitution 0.12**.
  낮은 반발이 핵심이다 — 안 튀고 "안착"해야 합체가 시원하게 보인다.

티어(11단): 반지름 0.30 / 0.40 / 0.54 / 0.68 / 0.82 / 1.00 / 1.18 / 1.38 / 1.62 / 1.90 / 2.20.
드롭으로 나오는 것은 티어 0~4 까지만(원작 준용).

형상: 전부 원으로 하면 굴러가는 그림이 단조롭다. 일부 티어는 볼록 폴리곤(planck 제한상 ≤8정점):
- oval  : 8각, 스케일 (0.82, 1.14)
- squat : 8각, 스케일 (1.16, 0.80)
- tear  : 상단 반원 6점 + 하단 꼭짓점 (0, -1.5r) = 7정점(아래로 뾰족한 딸기)
- pear  : 하단 반원 6점 + 상단 꼭짓점 (0, +1.35r) = 7정점
폴리곤 티어는 각도 a 가 눈에 보이므로 스냅샷에 각도를 반드시 담는다.

난수 금지. 드롭 스케줄은 정수 해시 LCG:
  SEED = (SEED * 1664525 + 1013904223) >>> 0 ;  rnd() = SEED / 2^32

머지 규칙:
- 매 서브스텝, 접촉 중인 **동일 티어 쌍**을 수집한다. 한 바디는 한 스텝에 한 번만 소비된다.
- 두 바디를 파괴하고 중점에 k+1 티어를 스폰. 속도는 두 부모의 평균, 단 **상승 성분은 제거**한다.
- 최고 티어끼리 만나면 소멸시킨다(신규 스폰 없음) → 보드가 비워지는 통쾌한 소거.
- 사건을 전부 기록한다: merges[{f,k,x,y,i}] · drops[{f,i,k,x}] · clears[{f,x,y,k}].

출력 `suika_snaps.json`:
{ meta:{fps,frames,sub,dt,seed,W,H,TOPLINE,wall}, tiers,
  frames: [ [ {i,k,x,y,a}, ... ] ],       // 프레임당 바디 배열. 좌표 4자리 반올림
  merges, drops, clears, gameOverF,
  validate:{ totalDrops,totalMerges,totalClears,maxTierReached,finalBodies,nan,outOfBounds } }

CLI: node suika_bake.cjs --frames 840 --fps 30 --seed 12345

검증 스크립트도 함께 작성해 아래를 출력하라:
  (a) 같은 인자 2회 베이크 → suika_snaps.json SHA256 동일
  (b) nan = 0 · outOfBounds = 0
  (c) 프레임 수·최고 도달 티어·최종 바디 수
````

**게이트 2**: (a)(b) PASS. (c)는 다음 STEP의 기준선으로 적어 둡니다.

> 좌표를 4자리로 반올림해 저장하는 것은 용량 때문만이 아닙니다. 렌더러가 읽는 값이 **텍스트로 고정**되므로, 스냅샷 파일만 같으면 어느 머신에서 그려도 같은 그림이 나옵니다.

## STEP 3 — ★게임오버 라인 규약 (이 저장소의 본론)

### 3.1 왜 규약이 먼저인가

수박게임에서 시청자가 가장 먼저 알아채는 결함은 **과일이 데드라인 위로 솟는 것**입니다. "게임오버 선"을 그려 놓고 그 위로 과일이 올라가면, 그 화면은 게임이 아니라 애니메이션입니다.

그런데 이 결함은 대부분 물리 버그가 아닙니다. **판정 반경을 잘못 잡아서** 생깁니다. 물리 반경으로 판정하면 화면에는 잎·꼭지까지 포함한 더 큰 실루엣이 그려지고, 눈에는 넘친 것으로 보입니다.

그래서 라인 규약을 **렌더 전에** 정의하고 **시뮬 불변식**으로 강제합니다.

### 3.2 불변식 4종

| # | 규칙 | 없으면 |
|---|---|---|
| ① | **판정 반경 = 렌더 실측 반경** `VIS_R[k]`(벡터 단위 최대반경 × 바디 확대율). 물리 반경이 아니다 | 화면에서만 넘침 |
| ② | **낙하 이후 과일은 라인을 넘지 못한다.** 초과분을 서브스텝마다 완만히 하향 보정 + 상승속도 제거 | 더미가 라인 위로 자람 |
| ③ | **신규 드롭 보류**: 안착 스택 top이 `TOPLINE − 0.30` 를 넘으면 드롭하지 않는다(난수 스트림도 소비하지 않는다) | 라인 위에서 게임이 계속됨 |
| ④ | **머지 산물 스폰 y 상한** = `TOPLINE − VIS_R[k+1]` (부모가 착지했을 때만 적용) | 큰 과일이 컨테이너 밖으로 솟아 HUD를 덮음 |

**"낙하 이후"의 정의가 이 STEP에서 가장 중요합니다.**

### 3.3 규약 프롬프트 (복사용)

````프롬프트
suika_bake.cjs 에 게임오버 라인 불변식을 추가해라. 렌더러가 아니라 **시뮬 안에서** 강제한다.

[상수]
  TOPLINE = (H - 1.6) * 1.1
  VIS_R[k] = 티어 k 의 **렌더 실측 최대 반경**(벡터 데이터의 단위 최대반경 × 바디 확대율).
             물리 반경 r 이 아니다. 렌더러와 같은 값을 쓰도록 한 곳에서 정의해 공유하라.
  GRACE_F = 60          // 생성 후 자유낙하 유예(프레임)
  DROP_HEADROOM = 0.30  // 안착 스택 top 이 TOPLINE - 이 값 넘으면 신규 드롭 보류
  SETTLE_CORRECT = 0.03 // 라인 초과분에 대한 **서브스텝당 최대 하향 보정(m)**
  REST_V = 1.2          // 안착 판정 속도(m/s)
  ATTRACT_CAP_G = 0.92  // 인력의 상향 성분 상한(중력 배수, <1)

[착지(landed) 판정 — ★여기서 틀리면 순간이동이 생긴다]
  착지 = 정적 바디(벽·바닥)와의 접촉, 또는 **이미 착지한 과일**과의 접촉.
  전이적으로 전파한다(A착지 & A-B접촉 → B착지). 고정점까지 최대 4패스 반복.
  ⛔ "모든 접촉"을 착지로 보면 안 된다. 슈트에서 자유낙하 중인 두 과일이 스치기만 해도
     착지로 처리되고, 라인 보정이 즉시 발동해 한 프레임에 수백 px 순간이동이 생긴다.
  머지 산물의 착지 여부는 **부모에게서 상속**한다(둘 다 미착지면 산물도 낙하 중).

[적용 순서 — 서브스텝마다]
  world.step(dt) → markLanded() → enforceTopline() → doMerges()

[enforceTopline]
  대상 = landed 이거나 생성 후 GRACE_F 프레임이 지난 바디.
  over = (y + VIS_R[k]) - TOPLINE ;  over > 0 이면 y 를 min(SETTLE_CORRECT, over) 만큼 내리고
  상승 속도(v.y > 0)를 0으로 만든다. ⛔ 한 번에 라인으로 투영(하드 클램프)하지 마라.

[동티어 인력을 쓸 경우]
  라인 근처(visTop > TOPLINE - 0.2) 바디는 인력 대상에서 제외.
  힘의 **상향 성분만** ATTRACT_CAP_G * g * mass 로 상한을 건다. 수평·하향은 무제한(캐스케이드 위력 보존).

[검증 스크립트 `check_topline.js` — 노출 프레임 전수 검사]
  각 프레임의 각 바디에 대해 y + VIS_R[k] <= TOPLINE 인지 본다.
  · landed 인데 초과 → VIOLATION
  · 미착지 + 생성 후 GRACE_F 이내 → WARN(유예 중 통과는 허용)
  결과를 "VIOLATIONS n · WARN m" 으로 출력하고, 위반 프레임·바디 id·초과량을 표로 찍어라.
````

**왜 보정에 상한을 두는가**: 하드 클램프는 물리 버그를 "가리는" 대신 **더 눈에 띄는 버그**로 바꿉니다. 참조 구현에서 초기 버전은 초과분을 한 번에 투영했고(사실상 무제한), 노출 구간에서 **1프레임 최대 318px 순간이동이 53건** 검출됐습니다. 서브스텝당 0.03m(=프레임당 0.12m)로 제한하니 0건이 됐습니다.

**게이트 3**
```
□ check_topline: VIOLATIONS 0 · WARN 0 (노출 구간 전 프레임)
□ 순간이동 검사(STEP 7의 check_snaps): 돌발 0건
□ ★프레임 스트립 육안: 라인 근처에서 과일이 "빨려 내려가는" 프레임이 없는가
```

> 이 부분은 "코드가 통과했다"와 "그림이 맞다"가 여러 번 갈렸던 자리입니다. 반드시 눈으로 봅니다.

## STEP 4 — authored 클라이맥스 (키스톤 사다리)

최고 티어에 자연 도달하려면 최소 과일 **1,024개**가 필요합니다. 20~30초 클립에서는 수학적으로 불가능합니다. 그래서 클라이맥스는 **authored 셋피스**로 만듭니다.

````프롬프트
suika_bake.cjs 에 두 페이즈를 넣어라.

[페이즈 A · 자연 빌드] f < KEY_START
- 0.42초 간격으로 티어 0~4 랜덤 드롭(LCG). x 도 LCG. 베이스 더미를 쌓는다.
- game-over 판정 활성(라인 위 바디가 거의 멈춰 있으면 gameOverF 기록).

[페이즈 B · 키스톤 사다리] f >= KEY_START
- 중앙에 키스톤 과일 하나를 세우고, **그 바로 위에서 같은 티어를 떨어뜨려** 낙하 머지로 한 칸씩 올린다.
- 머지가 일어나면 키스톤 id 를 산물에게 승계한다. 최고 티어까지 반복.
- 드롭 지점은 컨테이너 위(H + 0.6) — 데드라인 위에서 떨어뜨려야 낙하가 화면에 보인다.
- 이 페이즈는 의도적 고적재이므로 game-over 판정에서 제외한다.
- 간격 KEY_STEP(프레임)은 **음악 마디의 정수 분할**로 잡아라(STEP 8).

[측면 연속 드롭] 페이즈 B 내내, 0.28초 간격으로 far-side(|x| >= 2.1)에 소티어(0~2)를 떨군다.
- 중앙 사다리를 방해하지 않으면서 화면 전체가 계속 움직인다. 연쇄 머지도 여기서 나온다.
- LCG 스트림은 페이즈 A 와 같은 것을 이어 쓴다(스트림을 나누면 드롭 순서가 바뀌어 전체가 재배치된다).

[클리어 캐스케이드] f >= CLEAR_START
- 임의로 과일을 지우지 마라. **동티어 인력을 강하게 켜서 실제 머지 캐스케이드를 유도**하고,
  최고 티어끼리 만나 소멸하는 것으로 보드를 비운다(연출이 아니라 물리 결과).
- 인력 = 질량(r²)·거리 역제곱, 범위는 반경의 7배, 슬립 바디는 깨운다.
- 캐스케이드가 끝나면 소티어를 성기게 리필한다(새 사이클 시작감 = 루프 이음매).
- ⚠ 완전히 비우는 것은 물리적으로 보장되지 않는다(짝이 안 맞는 티어가 남는다). 남는 게 정상이다.

CLI 인자로 노출: --keyStart --keyStep --sideEvery --sideMaxK --clearStart --clearAttract --refillEvery
검증: 최고 티어 도달 · gameOver 미발생 · nan/oob 0 · 2회 베이크 SHA 동일.
````

## STEP 8 — 음악 그리드·심리스 루프 (선택) · 다른 게임으로 교체

### 음악에 붙이기

- 30fps · 180 BPM → **40프레임 = 1마디**. 씬 경계를 40의 배수로 잡으면 마디 정수가 유지됩니다.
- 키스톤 사다리의 등반 간격(`--keyStep`)을 마디의 정수 분할로 잡으면 합체가 박에 얹힙니다.
- 클라이맥스(최고 티어 완성)를 마디 첫 박에 놓으세요. 맞추는 방법은 **`BAKE_OFFSET` 하나를 움직이는 것**입니다 — 물리를 다시 굽지 않습니다.
- ⚠ 물리 파라미터를 바꾸면 클라이맥스 프레임이 이동하므로 **오프셋을 다시 유도**해야 합니다. 드롭 스케줄은 단일 LCG 스트림이라 하나만 바꿔도 전체가 재배치됩니다. "조금만 튜닝"이 안 되는 구조입니다.
- 루프를 만들 거면 **길이(초) × fps · × BPM/60 · × 44100 이 셋 다 정수**여야 합니다. 하나라도 소수면 루프 지점에서 미세하게 어긋납니다.
- 에너지 컨투어를 확인하세요. 구간별 RMS가 **평탄하면 실패**입니다. 클라이맥스 구간이 가장 커야 합니다.

### 심리스 루프

- 마지막 프레임의 베이크 위상과 첫 프레임의 베이크 위상이 **이어지도록** 매핑합니다(예: 끝 = bake N, 시작 = bake N+1).
- **정지 프레임(프리즈)을 두지 마세요.** 키스톤 사다리가 주기적으로 슈트에 과일을 떨어뜨리므로, 어떤 프레임을 얼려도 공중에 정지한 과일이 생깁니다. 프리즈 대신 슬로모·속도 램프를 쓰면 라인 게이트 WARN이 사라집니다.
- 게임오버 화면 같은 **종결 이벤트를 넣지 마세요.** 루프의 고리가 끊깁니다.

### 다른 게임으로 교체

게임 의존적인 파일은 `suika_bake.cjs` 와 `suika_render.js` 둘뿐입니다. 나머지(시크 하네스 · 캡처기 · 게이트)는 그대로 재사용됩니다.

1. 시뮬은 오프라인에서 **전체 타임라인을 미리 계산**하고, 렌더는 조회만 한다.
2. 클라이맥스 사건의 프레임을 밖으로 노출해 하네스가 거기에 맞출 수 있게 한다.
3. 루프가 필요하면 끝 위상 → 시작 위상 매핑을 만든다.
4. **"넘으면 안 되는 선"이 있는 게임이라면 그것을 판정 함수로 분리**하고, 렌더가 아니라 시뮬에서 강제한다. 그리고 노출 프레임 전수를 스크립트로 검사한다.
